> **Revision note:** This revision folds in confirmed, current (Oct 2026) Cloudflare documentation for Workers AI and R2 — exact binding syntax, exact model IDs, exact error codes, exact free-tier numbers, and the corrected upload/download architecture (a native R2 binding **cannot** issue presigned URLs; only the S3-compatible API with R2 API credentials can). ## 2. Architecture Overview

```
┌─────────────────────┐
│  React + TS (Vite)  │  ← Cloudflare Pages (static hosting)
│  built by AI Studio │
└─────────┬────────────┘
          │
          ├──── Supabase client (JS SDK) ─────► Supabase (Postgres + Auth + Realtime)
          │                                      - all user data, messages, profiles,
          │                                      - contacts, reactions, reports, admin tables
          │                                      - RLS enforced on every table
          │
          └──── fetch() to Worker API ─────────► Cloudflare Worker (single Worker, multiple routes)
                                                   - uploads: writes directly to R2 via the native
                                                     binding (env.MY_BUCKET) — simplest + most secure
                                                   - downloads: issues short-lived presigned GET URLs
                                                     via the S3-compatible API (aws4fetch + R2 API keys)
                                                   - proxies Cloudflare Workers AI calls (env.AI,
                                                     no credentials required)
                                                   - verifies the caller's Supabase JWT before
                                                     doing anything (see Section 5)
                                                         │
                                                         ├──► Cloudflare R2 (media files)
                                                         └──► Cloudflare Workers AI (inference)
```

**Why a Worker sits in front of R2 and Workers AI, instead of the frontend calling them directly:** The browser has no safe way to call either service. Workers AI's `env.AI` binding only exists inside a Worker's server-side execution context — there is no browser-callable endpoint for it, credentialed or not. R2's S3-compatible presigned-URL generation needs the account's R2 Access Key ID/Secret, which must never reach the browser. The Worker is the only component that holds those credentials (as Cloudflare secrets) and the only component allowed to call R2/Workers AI directly. The frontend always talks to Supabase directly (safe — Supabase's anon key + RLS is designed for this) and to the Worker for anything media- or AI-related.

## 4. Supabase Integration Strategy

- A single Supabase client is created once in `src/lib/supabaseClient.ts` using `createClient(import.meta.env.VITE_SUPABASE_URL, import.meta.env.VITE_SUPABASE_ANON_KEY)`.
- **No service-role key is ever used in the frontend.** All frontend reads/writes go through the anon key and are constrained entirely by RLS policies (see `05_Backend_Schema.md`).
- Supabase Auth session is read via `supabase.auth.getSession()` / `onAuthStateChange()`, wrapped in a single shared `AuthProvider` (React Context) — **not** a bare custom hook called independently in every component (see Section 11, "Known Pitfall").
- All table reads (messages, profiles, contacts, reactions, reports) go through the Supabase JS client directly — never through the Worker. The Worker is only for R2 and Workers AI.
- Supabase Realtime is used for:
  - **Postgres Changes** subscription on the `messages` table (filtered to the open conversation) for instant message delivery.
  - A **Presence** channel per user for online/offline status.
  - A **Broadcast** channel per conversation for the typing indicator (ephemeral, not stored in the DB).

## 5. Cloudflare Worker — API Surface

The Worker exposes a small, fixed set of routes. Every route first verifies the caller's Supabase JWT (passed as `Authorization: Bearer <token>`) against `SUPABASE_JWT_SECRET`, and extracts the caller's `user_id` from it. The Worker never trusts a `user_id` passed in the request body.

| Route | Method | Purpose | Workers AI model used |
|---|---|---|---|
| `/api/media/upload` | POST | `multipart/form-data` body: the file + `{ message_type }`. Worker validates size/type, writes the object straight to R2 via the native binding (`env.MY_BUCKET.put()`), and returns the object key the client should save to the `messages`/`profiles` row. **Not** a presigned PUT — the native binding cannot generate one; the Worker receives and writes the bytes itself, which is simple, secure, and well within the Worker's 100MB request-body limit for chat-sized media. | — |
| `/api/media/download-url` | POST | Body: `{ object_key }`. Server checks the caller is a participant in the conversation (or the object owner, for avatars), then returns a short-lived **presigned GET URL** generated via the S3-compatible API (`aws4fetch` + `R2_ACCESS_KEY_ID`/`R2_SECRET_ACCESS_KEY`), default 5-minute expiry. The browser downloads directly from R2 with this URL — no Worker proxying, no R2 egress cost either way. | — |
| `/api/ai/smart-reply` | POST | Body: `{ message_text }`. Returns 2–3 short suggested replies. | `@cf/meta/llama-3.1-8b-instruct-fast` |
| `/api/ai/translate` | POST | Body: `{ message_text, target_lang }`. Returns translated text. | `@cf/meta/m2m100-1.2b` |
| `/api/ai/summarize` | POST | Body: `{ messages: [...] }` (a bounded window of recent messages). Returns a short bullet-point summary. | `@cf/meta/llama-3.1-8b-instruct-fast` |
| `/api/ai/smart-search` | POST | Body: `{ query, messages: [...] }`. Embeds the query and the candidate messages, ranks by cosine similarity, returns matching message IDs. | `@cf/baai/bge-m3` |
| `/api/ai/moderate` | POST | Body: `{ content_type: 'text'\|'image', content }`. Called automatically only when a report is filed. Returns a moderation verdict + confidence score. | Text: `@cf/meta/llama-guard-3-8b` · Image: `@cf/meta/llama-3.2-11b-vision-instruct` |
| `/api/ai/transcribe` | POST | Body: `{ object_key }` (a voice note already in R2). Reads the object via the native R2 binding, base64-encodes it, transcribes it. Returns the transcript text. | `@cf/openai/whisper-large-v3-turbo` |
| `/api/ai/emoji-suggest` | POST | Body: `{ message_text }`. Returns 3–4 suggested emoji. | `@cf/meta/llama-3.1-8b-instruct-fast` |

**Exact `wrangler.jsonc` bindings for the Worker** (combined AI + R2, no API key needed for `AI`):
```jsonc
{
  "name": "inspire-worker",
  "main": "src/index.ts",
  "compatibility_date": "2026-10-22",
  "ai": { "binding": "AI" },
  "r2_buckets": [
    { "binding": "MY_BUCKET", "bucket_name": "inspire-media" }
  ],
  "vars": {
    "ACCOUNT_ID": "<cloudflare-account-id>",
    "BUCKET_NAME": "inspire-media"
  }
}
```

**AI budget safeguard (hard requirement for AI Studio to implement):**
- Every `/api/ai/*` route increments an `ai_usage_log` row in Supabase (feature name, neuron estimate, timestamp) *after* a successful call, so the Admin Analytics dashboard can show daily usage against the 10,000/day cap (the cap resets at **00:00 UTC** and is shared across the **entire Cloudflare account**, not per-Worker).
- Each `/api/ai/*` route first checks today's cumulative usage (a simple Supabase query) and returns `429 { error: "ai_budget_exceeded" }` if the app-wide daily estimate is already at/near the cap, so one busy day cannot silently blow the budget with no warning.
- Every `env.AI.run()` call is wrapped in try/catch. Known Workers AI failure modes to handle explicitly:
  - **Error 3036 / HTTP 429** — daily free Neuron allocation exhausted. Not retryable today; degrade and surface the budget-exceeded state.
  - **Error 3040 / HTTP 429** — GPU "out of capacity," transient. Safe to retry once, otherwise degrade gracefully.
  - **Error 5035 / HTTP 403** — the requested model requires the Workers Paid plan. None of the models chosen for this app (Section listed above) require it as of this writing, but the handler still checks for this code defensively.
- The frontend must treat any AI feature failure (network error, `429`, or Worker error) as **non-fatal**: hide the AI UI element gracefully, never block sending/reading messages.
- Admins can toggle any individual AI feature off app-wide from `/admin/settings` (see `05_Backend_Schema.md` → `app_settings` table); when a feature is off, the Worker route returns `403 { error: "feature_disabled" }` and the frontend must not attempt the call in the first place (check `app_settings` before showing the AI UI).

**Illustrative Worker-side pattern (`worker/src/ai.ts`, one handler shown):**
```ts
try {
  const result = await env.AI.run("@cf/meta/llama-3.1-8b-instruct-fast", {
    messages: [
      { role: "system", content: "Generate 2-3 short smart-reply suggestions." },
      { role: "user", content: messageText },
    ],
  });
  await logAiUsage(env, { feature: "smart_reply", estimated_neurons: 1 });
  return Response.json({ suggestions: result.response });
} catch (err) {
  const msg = err instanceof Error ? err.message : String(err);
  if (msg.includes("3036")) return Response.json({ error: "ai_budget_exceeded" }, { status: 429 });
  if (msg.includes("3040")) return Response.json({ error: "ai_temporarily_unavailable" }, { status: 503 });
  if (msg.includes("5035")) return Response.json({ error: "ai_requires_paid_plan" }, { status: 403 });
  return Response.json({ error: "ai_request_failed" }, { status: 500 });
}
```

## 6. Storage Strategy — Cloudflare R2

- One R2 bucket, `inspire-media`.
- Object key convention: `{user_id}/{uuid}.{ext}` for chat media, `{user_id}/avatar.{ext}` for profile photos (overwritten on re-upload).
- Nothing in R2 is public. Uploads go through `/api/media/upload` (Worker writes via the native binding). Reads go through `/api/media/download-url` (short-lived presigned GET URL, default 5-minute expiry, generated via the S3-compatible API since the native binding cannot sign URLs).
- File size limits (enforced both client-side before upload and server-side in the Worker):
  - Image: 10MB
  - Video: 50MB
  - Audio file: 20MB
  - Voice note: 10MB
  - Avatar image: 5MB
- Supabase's `messages.media_url` and `profiles.avatar_url` columns store the **R2 object key**, not a full URL (the full signed URL is resolved on demand via `/api/media/download-url`, since a stored public URL would defeat the point of signed access).
- Confirmed free-tier headroom for this app: **10GB-month storage, 1,000,000 Class A (write) ops/month (~33k uploads/day), 10,000,000 Class B (read) ops/month (~333k reads/day), and zero-cost egress** — comfortably enough for v1 usage without any cost risk.

## 7. Auth Approach

- Supabase Auth, email + password, with email verification required (`confirm email` enabled in Supabase Auth settings).
- On signup, after Supabase Auth creates the `auth.users` row, a corresponding `public.profiles` row is created (via a Postgres trigger — see `05_Backend_Schema.md`) with `username = NULL` initially; the user is routed to a "Choose your username" screen before reaching the main app, which does an `UPDATE profiles SET username = ...`.
- Session persistence: Supabase's default (`localStorage`, auto-refresh token) — no custom device-token logic needed or used (this replaces the old Netlify version's device-token approach entirely).
- Route protection: a single shared `AuthProvider` context gates all routes; `/admin/*` routes additionally require `profiles.role === 'admin'`, checked both client-side (hide the UI) and server-side (RLS — the actual data query fails for non-admins regardless of what the UI shows).

## 8. Security Requirements

1. No Supabase service-role key, Cloudflare R2 API token, or Workers AI credential ever appears in frontend code, `.env.example`, or any file committed to GitHub. These exist only as Cloudflare Worker secrets (set via `wrangler secret put`, documented but not executed by AI Studio) and Supabase server-side config. **Note:** Workers AI itself requires no credential at all (it is a native, zero-config Worker binding) — the only genuinely secret values in this stack are the Supabase service-role key and the R2 S3 API keys.
2. Every Supabase table has RLS enabled with explicit policies — no table is left with RLS disabled "temporarily." See `05_Backend_Schema.md`.
3. The Worker independently verifies the Supabase JWT on every request; it never trusts client-supplied identity.
4. All media access is via Worker-mediated writes and short-lived presigned reads; the R2 bucket itself has no public access.
5. Admin routes are enforced server-side (RLS + Worker checks), not just hidden in the UI.
6. The `admin_audit_log` table (chat history access logging) is append-only from the frontend/Worker's perspective — no update/delete policy is granted to any role except via direct database admin access (outside the app).

## 11. Known Pitfall From the Previous Build (Must Be Avoided)

A prior version of this app (built on a different, now-abandoned Netlify-based stack) shipped with a critical bug: `useAuth` was implemented as a **plain custom hook** (not a React Context), and every page independently called `useAuth()`, creating **disconnected copies of auth state** that never synced with each other — leading to broken login/redirect flows.

**Hard requirement for this rebuild:** Auth state (`useAuth`) **must** be implemented as a single `AuthProvider` (React Context) wrapping the whole app in `App.tsx`, with `useAuth()` as a `useContext` consumer — never a standalone `useState`-based hook called independently per page. The same file (`useAuth.tsx`, note the `.tsx` extension since it contains JSX for the Provider) must be used everywhere auth state is needed.

**Second pitfall to avoid (new, surfaced during this revision's Cloudflare research):** do not assume the native R2 binding (`env.MY_BUCKET`) can generate a presigned/signed URL — it cannot. Only the S3-compatible API (via `aws4fetch` + `R2_ACCESS_KEY_ID`/`R2_SECRET_ACCESS_KEY`) can sign URLs. The architecture in Sections 5–6 above (native binding for uploads, S3 API for presigned downloads) is the corrected, confirmed pattern — do not revert to a single "ask the Worker for a signed PUT URL via the native binding" design, as that is not possible.

## 12. API/Service Requirements Summary

- Supabase JS SDK (`@supabase/supabase-js`) — DB queries, Auth, Realtime.
- `fetch()` to the Worker for media uploads/downloads and all AI calls — no other third-party SDKs on the frontend.
- `aws4fetch` — a single lightweight dependency inside `worker/`, used only to sign R2 download URLs. Not a frontend dependency.
- No Express, no custom Node server, no Netlify-specific packages (this is a clean break from the old stack).
